# Проектирование бэкенда

Статус: предложение архитектуры первой версии. Документ описывает будущую реализацию; сервер и окружение пока не созданы. Источники требований: `VISION.md`, `schemas/recipe.schema.json`, `docs/recipe-format.md`. Общие решения описаны в архитектурном документе проекта; HTTP-контракт — в `docs/api-contract.md`.

## Границы и стек

Один Python-сервис FastAPI обслуживает Telegram Mini App: авторизацию, рецепты, справочник продуктов, чаты и обращения к модели. React-клиент и `/api/v1` публикуются под одним HTTPS-origin. Отдельный Node.js-сервер не нужен. Для разработки используем окружение pyenv с именем `RecipeBook`; зависимости и их зафиксированные версии описываются в `pyproject.toml` и lock-файле. Команды разработки должны проверять выбранное окружение, не устанавливать зависимости в системный Python.

SQLAlchemy отвечает за доступ к SQLite, Alembic — за миграции. Один процесс приложения и постоянный диск достаточны для первой версии. Короткие синхронные операции БД выполняются вне event loop; ожидание модели не удерживает соединение или транзакцию. Не вводим брокер сообщений, отдельный worker, Redis или абстрактный универсальный репозиторий до появления задачи, которая их требует.

## Модули

```text
backend/
  pyproject.toml
  migrations/
  src/recipebook/
    main.py                 # сборка приложения, lifespan, маршруты
    config.py               # Settings, чтение env, проверка конфигурации
    api/                    # routes, HTTP schemas, dependencies, errors
    domain/                 # RecipeContent, quantities, semantic validation
    services/               # RecipeService, ConversationService, auth, drafts
    repositories/           # SQLAlchemy queries, atomic revision updates
    db/                     # ORM tables, engine, session factory
    llm/                    # provider protocol, LangChain adapter, prompts
  tests/
```

Повторяющиеся правила живут в функциях валидации; состояние и зависимости — в небольших сервисах (`RecipeService`, `ConversationService`). HTTP-обработчик проверяет вход, вызывает сервис и возвращает результат. Сервис не зависит от FastAPI Request. `RecipeAssistant` скрывает LangChain и провайдера от остального кода. Для тестов зависимости подменяются явным внедрением, без глобального клиента LLM.

## Контракты и валидация

`RecipeContent` соответствует существующей JSON Schema, включая `userNotes`. Python использует snake_case внутри и camelCase в JSON. Публичная схема не расширяется полями базы или провайдера. Pydantic-модели и JSON Schema должны проверяться на совместимость контрактными тестами; нельзя независимо менять оба формата без проверки. Схема провайдера может отличаться, но адаптер всегда преобразует её в канонический объект.

`RecipeRecord` — оболочка: `id` (UUID), `revision` (целое, начинается с 1), `createdAt`, `updatedAt` (UTC, ISO 8601), `source` (`manual` или `llm`, источник создания), `sourceConversationId` (nullable), `content: RecipeContent`. Изменение вручную не переписывает историю происхождения. При необходимости различать происхождение каждого обновления добавляется отдельное поле, а не меняется смысл `source`.

Кроме JSON Schema проверяем `activeMinutes <= totalMinutes`, границы диапазонов, уникальные ID элементов, ссылки шагов на существующие ингредиенты, текст после trim, конечность чисел. Неиспользованный в шагах ингредиент — предупреждение. Настраиваем ограничения размера тела запроса, числа элементов, длины текстов и истории до отправки модели; конкретные пределы закрепляются при реализации и документируются клиенту.

Ручная незавершённая форма не является `RecipeContent`: первая версия сохраняет её локально на клиенте. API принимает только полноценный рецепт. Пересчёт порций и состояние готовки не изменяют серверный рецепт. Личные заметки не включаются в запросы модели по умолчанию.

## Хранение

| Таблица | Основные данные и назначение |
|---|---|
| `recipes` | ID, revision, timestamps, source, source_conversation_id; канонический `content_json`; индексируемые title/search_title, total_minutes, active_minutes |
| `products` | ID, отображаемое имя и уникальное нормализованное имя |
| `product_aliases` | Уникальный нормализованный alias и product_id |
| `recipe_ingredients` | recipe_id, local_ingredient_id, product_id; составной уникальный ключ (recipe_id, local_ingredient_id) |
| `conversations` | ID, даты, необязательная ссылка на рецепт |
| `messages` | ID, conversation_id, порядковый номер, role, текст, структурированный ответ; уникальный номер в чате |
| `generation_requests` | ID, conversation_id, уникальный для пользователя client_request_id, status, base_recipe_id/revision, timestamps, код ошибки |
| `recipe_drafts` | ID, generation_request_id, проверенное содержимое без userNotes, дата, nullable saved_recipe_id, saved_at, saved_target_id (для защиты повторов после удаления рецепта) |
| `sessions` | Хеш случайного токена сессии, telegram_user_id, срок действия |
| `idempotency_records` | Ключ операции, хеш входа, сохранённый результат; защита от повторного сохранения |

Канонический JSON — источник истины рецепта. Поля фильтров и связи ингредиентов являются проекциями, обновляются в той же транзакции и могут быть перестроены. Порядок и группировки остаются в JSON, поэтому не нужно собирать рецепт из множества таблиц. `userNotes` хранится в JSON вместе с содержимым; при применении LLM-черновика сервис берёт заметки из актуальной записи.

Нормализация продукта: trim, приведение регистра, согласованная обработка `ё/е`, схлопывание пробелов. Не объединяем «томат» и «томатная паста» по догадке модели. Точное совпадение имени/alias привязывается автоматически; неизвестное имя создаёт отдельный продукт. Для будущих синонимов и ручной корректировки связей предусмотрены aliases и сервис переназначения; автоматической лемматизации и семантического поиска для старта не требуется.

Включаем foreign keys, задаём busy timeout, WAL для локального диска. Индексы нужны по времени, дате обновления, связям recipe/product и conversation/message. Для русского поиска используем нормализованное `search_title`, а не полагаемся на встроенный ASCII `NOCASE`. Поиск по названию в маленькой библиотеке допускает подстроку. Сортировка стабильна по `(updated_at, id)`.

Удаление рецепта каскадно удаляет связи ингредиентов, но сохраняет чат; его ссылка на рецепт обнуляется. Исторический draft сохраняется, ссылка `saved_recipe_id` обнуляется, но saved_at и сохранённая цель остаются для обнаружения повторного save после удаления рецепта. Резервная копия создаётся SQLite backup API или согласованным снимком, а не копированием только основного файла при открытом WAL. Процедура восстановления проверяется отдельно. PostgreSQL не нужен сейчас; избегаем специфичного SQL там, где это не усложняет код.

## Предлагаемый HTTP API

| Метод и путь `/api/v1` | Назначение |
|---|---|
| `POST /auth/telegram` | Проверить `initData`, создать сессию |
| `GET /me` | Проверить сессию и вернуть минимальные данные пользователя |
| `POST /auth/logout` | Удалить сессию и cookie |
| `GET /recipes` | Список кратких карточек: q, totalMinutesMax, activeMinutesMax, повторяемый productIds, limit, cursor |
| `POST /recipes` | Ручное создание из RecipeContent, 201 + RecipeRecord |
| `GET /recipes/{id}` | RecipeRecord и ETag |
| `PUT /recipes/{id}` | Ручная полная замена content с If-Match |
| `PATCH /recipes/{id}/notes` | `{userNotes}`, If-Match; сохранить заметки отдельно от редактора |
| `DELETE /recipes/{id}` | Удалить с If-Match, 204 |
| `GET /products?q=...` | Варианты продуктов для фильтра, ID и название |
| `POST /conversations` | Создать чат, опционально recipeId |
| `GET /conversations` | Список чатов с пагинацией |
| `GET /conversations/{id}` | Метаданные чата |
| `DELETE /conversations/{id}` | Удалить чат, сообщения и draft; 409 при running |
| `GET /conversations/{id}/messages` | История сообщений с пагинацией |
| `POST /conversations/{id}/messages` | message, clientRequestId, опционально актуальный recipe context; получить ответ и nullable draft |
| `GET /generation-requests/{id}` | Статус/результат для восстановления после сетевого сбоя |
| `POST /drafts/{id}/save` | Сохранить draft новым рецептом или применить к существующему |

Список рецептов возвращает `{items, nextCursor}`; item содержит ID, revision, title, servings, time, updatedAt. Фильтр нескольких productIds означает наличие **всех** выбранных продуктов; необязательные ингредиенты тоже участвуют. Это поиск по составу, не обещание приготовить блюдо только из выбранного набора.

В первой версии ответ чата — обычный JSON после завершения запроса с ограниченным временем ожидания. Формат ответа модели и chat response уточняется в документе интеграции. Один активный запрос на чат; новый конкурентный запрос возвращает 409. Pending фиксируется до вызова LLM, затем результат и draft фиксируются одной короткой транзакцией. После перезапуска оставшиеся running помечаются interrupted; скрытый автоматический повтор платного вызова не выполняется.

`POST /drafts/{id}/save` принимает `{targetRecipeId: null | UUID}` и Idempotency-Key; при замене обязателен If-Match. Без target создаёт рецепт, `userNotes = ""`. С target обязательно проверяет If-Match и baseRevision черновика и сохраняет текущие userNotes. Версия, на основе которой модель готовила изменение, хранится вместе с draft и не должна незаметно подменяться последней версией. Draft становится рецептом только после явного действия пользователя. Повтор того же ключа и тела возвращает прежний результат, другой payload с тем же ключом — 409.

## Одновременные правки и ошибки

GET одного рецепта возвращает ETag с revision. PUT/PATCH/DELETE требуют If-Match; отсутствие — 428, несовпадение — 412. Обновление атомарно: `UPDATE ... WHERE id = ... AND revision = expected`; проверка в Python до отдельного UPDATE недостаточна. Изменение содержимого, заметок и проекций коммитится вместе, revision увеличивается один раз. Клиент при конфликте сохраняет свой ввод и предлагает загрузить новую версию; сервер не объединяет тексты автоматически.

Ошибки имеют вид `{error: {code, message, requestId, details}}`. Для ошибок полей details содержит безопасные пути и описания, без исходных секретов и полного запроса провайдеру. 401 — нет/истекла сессия, 403 — чужой Telegram ID, 404 — нет записи, 409 — занятый чат/конфликт идемпотентности, 412 — версия изменилась, 422 — невалидный ввод, 429 — лимит запросов, 502 — ошибка/невалидный ответ модели, 504 — таймаут модели. UI использует стабильный code; внутренние traceback и сообщения SDK остаются на сервере с редактированием чувствительных полей.

## Авторизация и конфигурация

Сервер принимает исходную строку Telegram initData, проверяет подпись по официальному алгоритму Telegram и возраст auth_date, затем сравнивает user.id с `TELEGRAM_ALLOWED_USER_ID`. Данные из initDataUnsafe не являются доказательством личности. Конкретную реализацию подписи сверяем с актуальной документацией Telegram и проверяем тестовыми векторами при реализации. Подпись проверяется сравнением с постоянным временем. Сроки допуска и сессии задаются настройками, сервер проверяет их при каждом запросе.

После входа выдаётся случайный непрозрачный токен в Secure/HttpOnly/SameSite cookie с Path=/; в БД хранится только его хеш. Сессия не продлевается бесконечно. Токен не попадает в localStorage. Изменяющие запросы проверяют Origin; разрешён только origin приложения, CORS не открывается на `*`. Выход выполняется POST. Для разработки допустима отдельная тестовая auth dependency, отключённая по умолчанию и запрещённая при production-конфигурации.

Все секреты и чувствительная конфигурация находятся в локальном `.env`, исключённом из Git: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ALLOWED_USER_ID`, `LLM_API_KEY`. Несекретные настройки также можно задавать там: `APP_ENV`, `PUBLIC_APP_URL`, `DATABASE_URL`, `LLM_PROVIDER`, `LLM_MODEL`, необязательный `LLM_BASE_URL`, `LLM_TIMEOUT_SECONDS`, `LLM_MAX_OUTPUT_TOKENS`, `LLM_MAX_CONVERSATION_TOKENS`. `.env.example` содержит только названия и безопасные заглушки. Приложение не выводит Settings целиком. БД, резервные копии, `.env` и сырые чаты не попадают в Git; права на файл `.env` ограничиваются владельцем. В браузерном VITE_* нет ключей, bot token или Telegram ID для контроля доступа.

## Проверки реализации

- Валидация RecipeContent: существующий пример, некорректные диапазоны, active > total, дубли ID, битые ссылки, лишние поля, текст из пробелов.
- Контракт: пример проходит JSON Schema и Pydantic; экспорт OpenAPI соответствует клиентским типам; преобразование провайдерского draft не включает заметки.
- Интеграционные тесты с временной файловой SQLite: CRUD, транзакционное обновление индексов, фильтр всех продуктов, пагинация, миграция пустой БД.
- Две конкурирующие записи с одной revision: одна успешна, вторая получает конфликт; аналогично заметки против применения draft.
- Auth: испорченная подпись, истекший auth_date, чужой ID, истекшая сессия, запрещённый Origin; production не запускается с dev auth.
- LLM через fake adapter: таймаут, отказ, неверный JSON, семантическая ошибка, повтор clientRequestId, обрыв сети, восстановление interrupted, сохранение заметок и защита от двойного сохранения.
- Резервная копия и восстановление: после восстановления доступны рецепт, поиск и ссылки ингредиентов. Живой API модели для основной тестовой серии не требуется.

Неразрешённых блокирующих продуктовых вопросов в рамках этого предложения нет. Выбор хостинга, модели и провайдера оплаты понадобится перед запуском, но не мешает определить границы и контракт.
