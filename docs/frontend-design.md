# Фронтенд RecipeBook

Статус: проект архитектуры первой версии. Документ описывает будущую реализацию; приложение ещё не реализовано. Основание: `VISION.md`, `schemas/recipe.schema.json` и согласованный макет `recipe-layout.html`.

## Границы и технологии

React + TypeScript + Vite, клиентское приложение внутри Telegram Mini App. Один Python-бэкенд обслуживает авторизацию, данные и модель. Фронтенд обращается к `/api/v1` на том же origin; в разработке Vite проксирует этот путь в локальный бэкенд. Python-окружение фронтенду не требуется; зависимости Node изолируются в `frontend/node_modules`, версии фиксируются lock-файлом.

Предлагаемые библиотеки: React Router для маршрутов, TanStack Query для серверных данных, React Hook Form для редактора. Стили — обычный CSS с переменными и локальными классами: для небольшого приложения дополнительная система компонентов не обязательна. Конкретные версии закрепляются при реализации после проверки совместимости.

Типы API генерируются из OpenAPI FastAPI. Не создаём вторую вручную поддерживаемую модель рецепта в TypeScript. Канонические ограничения проверяет сервер; клиент добавляет удобную проверку формы до отправки. Незавершённый `RecipeFormState` — отдельный тип, допускающий пустые поля и строки вместо чисел.

## Навигация и экраны

Основная навигация: «Рецепты» и «Чат». Кнопка «Создать» в библиотеке открывает ручной редактор. Системная кнопка Telegram «Назад» и кнопка приложения вызывают один механизм навигации; подписки снимаются при размонтировании.

| Маршрут | Содержимое и действия |
| --- | --- |
| `/recipes` | Поиск по названию, фильтры, список кратких карточек, создание вручную |
| `/recipes/new` | Пустой редактор, сохранение нового рецепта |
| `/recipes/:id` | Название и время, ингредиенты, приготовление, заметки; редактирование и обсуждение с моделью |
| `/recipes/:id/edit` | Ручное редактирование сохранённого содержимого |
| `/chat` | Начало нового диалога и список сохранённых диалогов с сервера |
| `/chat/:conversationId` | Сообщения, идеи блюд, проверенный черновик рецепта |

### Библиотека

Карточка содержит название и время в формате `25 мин (15 мин)`. Без декоративных категорий и автоматически придуманных тегов. Карточка целиком открывает рецепт.

Строка поиска и отдельная кнопка «Фильтры». В фильтрах: максимум общего времени и продукты из серверного справочника с поиском. Несколько продуктов означают «содержит все выбранные продукты». Этот смысл указан рядом с фильтром, а сам фильтр применяется сервером. Фильтры сохраняются в URL, поэтому возврат из рецепта восстанавливает список. Требуются пагинация и стабильный порядок выдачи.

Пустая библиотека предлагает создать рецепт или начать чат. Пустой результат поиска предлагает сбросить фильтры, не выглядит ошибкой.

### Просмотр рецепта

Порядок соответствует принятому макету:

1. Светло-оливковая плитка с названием и общим временем; активное время только в скобках.
2. Белая плитка ингредиентов, выбор порций и отметки подготовленных продуктов.
3. Переключатель «По шагам / Лента» и приготовление.
4. Личные заметки с горчичной вертикальной линией. Пустые заметки заменяются компактным действием «Добавить заметку».

В режиме «По шагам» видна одна карточка: `ШАГ 1`, заголовок, инструкция, необязательная длительность таймера. Кнопки «Назад» и «Далее» доступны независимо от жестов; на границах соответствующая кнопка отключена. Последний шаг не сохраняет и не изменяет рецепт автоматически. В режиме «Лента» тот же компонент карточки повторяется для всех шагов; страница прокручивается естественно. При переключении сохраняется текущий шаг, а лента прокручивается к нему по явному переключению режима, не при каждом рендере.

Повторные списки ингредиентов в шагах по умолчанию не показываем, как в очищенном макете. Ссылки `ingredientIds` остаются в данных для редактора и проверки целостности. Длительность `timerSeconds` в первой версии — подпись; работающий таймер и фоновые уведомления не обещаются.

При показе рецепта из чата добавляются действия «Сохранить» и «Редактировать». Если он создан как изменение существующего рецепта, явно различаем «Применить к рецепту» и «Сохранить копию». До этого сохранённая запись не изменяется.

### Ручной редактор

Последовательные секции: название, порции, общее и активное время, ингредиенты, шаги, личные заметки. Форма работает без модели. Обязательные поля не скрыты в раскрывающихся панелях.

В строке ингредиента выбирается тип количества: точное, диапазон, по вкусу, по необходимости. Числовые поля и единицы показываются только там, где нужны. Подготовка, группа и необязательность доступны через дополнительные поля строки. При смене типа количества несовместимые поля исключаются из отправляемого объекта.

Шаг содержит заголовок, инструкцию, выбор ингредиентов и необязательную длительность таймера. Добавление, удаление и перемещение строк выполняются обычными кнопками; drag-and-drop не является единственным способом. ID элемента генерируется один раз, соответствует схеме и сохраняется при переименовании и перестановке. При удалении ингредиента форма показывает затронутые шаги и удаляет соответствующие ссылки, но пользователь проверяет текст инструкций самостоятельно.

Ошибки показываются у полей; после неудачного сохранения фокус переходит к первой ошибке. Перед уходом из изменённой формы предлагаются сохранение, выход без сохранения и продолжение редактирования. На закрытие WebView нельзя полагаться как на гарантированный момент сохранения. В первой версии незавершённая форма держится в памяти текущей сессии; постоянное хранение черновиков требует отдельного решения и не подразумевается.

### Чат

Сообщение модели может содержать текст, идеи и проверенный черновик. Идеи отображаются простыми кнопками с названием и кратким описанием. Выбор идеи отправляет обычное сообщение с контекстом выбранного варианта. Черновик использует общий компонент рецепта, а не отдельную разметку из Markdown.

Первая версия получает полный JSON-ответ без потокового UI. Пока запрос выполняется, виден спокойный индикатор «Готовлю ответ», повторная отправка отключена, уже полученная история доступна. Пустые или частичные поля рецепта не показываются как готовый результат. Личные заметки не отправляются модели автоматически. Смена страницы не должна создавать второй запрос и второй рецепт.

## Компоненты и структура кода

```text
frontend/src/
  app/                  # маршруты, провайдеры, начальная авторизация
  api/                  # генерируемые типы, HTTP-клиент, ошибки
  platform/telegram/    # адаптер Telegram и заглушка для локальной разработки
  features/
    recipes/            # библиотека, запросы, сохранение, просмотр
    recipe-editor/      # состояние незавершённой формы и преобразование в API
    chat/               # сообщения, идеи, черновик модели
  shared/
    recipe/             # визуальные части рецепта и чистые функции
    ui/                 # Button, Field, Panel, EmptyState, ErrorNotice
    styles/             # токены цветов, размеры, типографика
```

Общие компоненты рецепта: `RecipeSummary`, `IngredientList`, `IngredientRow`, `ServingsControl`, `StepCard`, `StepViewer`, `RecipeNotes`, `RecipeView`. Они получают данные и callbacks через props, не знают о Telegram и не вызывают LLM. Экран связывает компоненты с API. Одно представление рецепта используется в библиотеке, предпросмотре формы и чате с различными доступными действиями.

Чистые функции: `scaleQuantity`, `formatQuantity`, `formatDuration`, `groupIngredients`, `toRecipeContent`, `mapApiValidationErrors`. Хуки: `useCookingSession`, `useRecipe`, `useRecipeMutations`, `useTelegramNavigation`. Классы для React-компонентов не нужны; адаптер платформы и HTTP-клиент получают явные интерфейсы, позволяющие подставлять реализации в тестах.

## Состояние и пересчёт

| Состояние | Владелец и срок жизни |
| --- | --- |
| Рецепты, ревизии, чат | Сервер; TanStack Query кэширует ответы |
| Поиск и фильтры | URL |
| Несохранённая форма | Состояние редактора в текущей сессии |
| Порции, отмеченные ingredient IDs, текущий step ID | Отдельная сессия приготовления для recipe ID + revision |
| Предпочтение «По шагам / Лента» | Локальная настройка, допустимо хранить только её в localStorage |

Сессия приготовления не меняет `RecipeContent`. При новой ревизии рецепта она сбрасывается, чтобы отметки и шаги не относились к изменённому содержимому. В первой версии её не синхронизируем между устройствами.

Порции выбираются в пределах схемы 1–100; ограничение макета до 8 не переносится в приложение. Коэффициент — выбранные порции / исходные порции. Пересчитываются точные количества и оба края диапазона; исходные числа не мутируются. `to_taste` и `as_needed` остаются текстом. Время и таймеры не масштабируются. Дробные штуки не округляются до целых. Округление применяется только при форматировании: до двух знаков с увеличением точности для положительных значений меньше 0,01, чтобы количество не превратилось в ноль. Единицы не конвертируются автоматически.

## API-контракт

Контракт согласован на уровне проекта с бэкендом; единый источник маршрутов и форматов — `docs/api-contract.md`, затем OpenAPI реализации. HTTP-клиент использует общие обработку ошибок и credentials, а не собственный fetch в каждом компоненте.

| Операция | Контракт |
| --- | --- |
| Вход | `POST /api/v1/auth/telegram` с `initData`; сервер устанавливает HttpOnly cookie |
| Текущая сессия | `GET /api/v1/me` |
| Библиотека | `GET /api/v1/recipes`, фильтры `q`, `totalMinutesMax`, `productIds`, параметры пагинации |
| Создание | `POST /api/v1/recipes` с полным `RecipeContent` и разрешёнными сервером сведениями об источнике |
| Чтение | `GET /api/v1/recipes/{id}` → `RecipeRecord` |
| Сохранение | `PUT /api/v1/recipes/{id}` с полным `RecipeContent`, `If-Match` исходной ревизии |
| Заметки | `PATCH /api/v1/recipes/{id}/notes`, `If-Match`; без обращения к модели |
| Удаление | `DELETE /api/v1/recipes/{id}`; только после явного действия пользователя |
| Продукты | `GET /api/v1/products?q=...` |
| Новый чат | `POST /api/v1/conversations` |
| Список чатов | `GET /api/v1/conversations` |
| История | `GET /api/v1/conversations/{id}` для метаданных, `GET /api/v1/conversations/{id}/messages` для сообщений с пагинацией |
| Запрос модели | `POST /api/v1/conversations/{id}/messages` → сообщение, идеи, необязательный `recipeDraft` |
| Сохранение черновика модели | `POST /api/v1/drafts/{id}/save` с `{targetRecipeId: null \| string}`, `Idempotency-Key`; при замене также `If-Match` |

`RecipeRecord` содержит `id`, `revision`, даты, `source`, `sourceConversationId` и `content`. Краткая выдача библиотеки не должна требовать загрузки всех шагов каждого рецепта. Исходная ревизия сохраняется при начале редактирования; после успешного сохранения клиент обновляет кэш и новую ревизию. Сохранение черновика модели всегда является отдельным действием пользователя через `/drafts/{id}/save`; `targetRecipeId: null` создаёт копию, ID существующего рецепта заменяет его содержимое с сохранением личных заметок на сервере.

Ответ чата — `{message, ideas, recipeDraft}`, где `recipeDraft` равен `null` либо содержит `{id, baseRecipeId, baseRevision, content}`. Его `content` не содержит `userNotes`. Общий `RecipeView` принимает содержимое для чтения и заметки отдельным необязательным prop: отсутствие заметок в черновике не нужно маскировать фиктивным полем. Редактирование черновика перед сохранением использует обычную форму нового рецепта либо форму существующего рецепта с его актуальными заметками; сохранение проходит стандартный контракт ручного редактирования и проверку ревизии.

Для поддерживающих идемпотентность операций используется `Idempotency-Key`: один ключ на одно намерение, повтор того же запроса использует тот же ключ. Пока операция не завершилась, кнопка отключена. Автоматические повторы изменяющих запросов не допускаются без этой гарантии. Поддержка ключа каждым endpoint и формат пагинации определены в единой API-документации.

## Ошибки и конкурентные изменения

- Ошибка сети: сохраняем введённый текст, показываем повтор рядом с действием. Не сообщаем об успешном сохранении до ответа сервера.
- Истёкшая сессия: повторяем авторизацию через Telegram; при недоступных или отклонённых данных показываем экран повторного открытия Mini App.
- Доступ запрещён: отдельное короткое сообщение без формы и бесконечных повторов.
- Рецепт удалён: сообщение и возврат в библиотеку.
- Ошибка полей: отображаем серверные пути ошибок рядом с соответствующими полями формы.
- Конфликт ревизии (`412`): сохраняем локальные изменения в памяти, предлагаем загрузить актуальную запись или сохранить локальный вариант копией. Не перезаписываем новую версию молча.
- Ошибка модели, лимит или неподходящий ответ: история и сохранённый рецепт остаются доступными, объясняем причину кратко, предлагаем явный повтор. Не показываем сырой ответ провайдера или stack trace.

Состояния ошибок объясняют конкретное действие. Технические идентификаторы запроса доступны для диагностики, но не загромождают основной экран.

## Визуальные правила и доступность

Единый `system-ui, sans-serif`. Прямые углы у плиток, кнопок и полей. Основные цвета из текущего макета: белый `#ffffff`, почти чёрный `#191a17`, оливковый `#707c42`, терракотовый `#ad503b`, горчичный `#e6c66b`. Светлый фон страницы `#f5f5f0`, плитка названия `#eef1e3`, остальные плитки белые. Цвета — CSS-переменные, проверяются на контраст при реализации.

Разделение создают фон плиток, промежутки 12–16 px и внутренние отступы 18–20 px; не множество рамок. Оливковый — основное действие, терракотовый — номер шага и редкие акценты, горчичный — заметки и длительность. Удаление всегда обозначено текстом, цвет не является единственным сигналом. Не добавляем категории «На каждый день», разделитель `·`, надпись «ИЗ 4» и подпись «активной готовки» в видимом тексте карточки.

Кликабельные области не меньше 44 px, заметный keyboard focus, настоящие labels и кнопки, логичные заголовки. Для времени доступное описание поясняет общее и активное время, хотя визуально остаются только числа. Учитываем safe area, экранную клавиатуру и изменение высоты Telegram WebView. Проверяем ширину 320–430 px, длинные русские названия и масштабирование текста. Жесты и hover не обязательны для выполнения действий.

## Безопасность и конфигурация

Все токены, cookie secrets и ключи модели находятся только в серверном `.env`. `.env` исключён из Git; `.env.example` содержит только имена и безопасные примеры. В `VITE_*` нельзя помещать секреты: значения попадут в клиентскую сборку. Фронтенду достаточно относительного `/api/v1`; публичная конфигурация допускается только для несекретных параметров.

`initData` получается из Telegram во время работы, отправляется серверу для проверки и не сохраняется в localStorage, логах или URL. Клиент не доверяет `initDataUnsafe` для контроля доступа. Авторизация через cookie требует серверной защиты изменяющих запросов от CSRF; клиент передаёт соответствующий токен, если его предусматривает единый API. Cookie HttpOnly и не читается JavaScript.

Текст пользователя и модели рендерится как текст, без `dangerouslySetInnerHTML`. Если позже потребуется Markdown, используется ограниченный безопасный renderer. Mock-адаптер разработки не создаёт обход серверной авторизации в production. История чата и содержимое рецептов не пишутся в стороннюю аналитику.

## Проверки при реализации

Проверяем функции пересчёта на точных, диапазонных и текстовых количествах, дробных штуках и малых значениях. Проверяем преобразование незавершённой формы, сохранность ID при перестановке, удаление ссылок на ингредиенты и отображение серверных ошибок.

Интеграционные сценарии: создание и редактирование без LLM; сохранение черновика модели только по кнопке; конфликт двух устройств; повтор после сетевого сбоя без дубликата; оба режима шагов с одним состоянием порций. В Telegram проверяем вход, «Назад», клавиатуру и safe area на телефоне. До полноценного backend UI можно разрабатывать через mock HTTP, совпадающий с OpenAPI, не обращаясь к настоящей модели.
