# Архитектура RecipeBook

Рабочий проект первой версии от 24 октября 2026 года. Приложение ещё не реализовано. Продуктовые требования — в VISION.md, формат рецепта — в schemas/recipe.schema.json.

## Основные решения

Один Python-бэкенд FastAPI обслуживает Telegram Mini App на React + TypeScript + Vite. SQLite хранится на постоянном диске сервера; SQLAlchemy отвечает за доступ, Alembic — за миграции. Pydantic описывает и проверяет данные. LangChain используется внутри сменного адаптера модели. Сервисы, очереди, Redis, векторная база и агентный цикл для первой версии не нужны.

В разработке Vite проксирует /api к FastAPI. В размещённом приложении фронтенд и /api доступны с одного HTTPS origin через reverse proxy. Браузер не обращается к провайдеру LLM и базе напрямую. Telegram-бот служит точкой входа в Mini App; отдельный постоянно работающий процесс бота для одной кнопки открытия не требуется.

## Границы модулей

Поток: HTTP route → application service → repository/provider adapter. Роуты преобразуют HTTP в команды приложения; сервисы реализуют сценарии и транзакции; репозитории работают с SQLAlchemy. Доменные модели не зависят от FastAPI или LangChain.

Классы нужны для объектов с зависимостями или состоянием: настройки, сервис рецептов, репозиторий, провайдер модели. Валидация, нормализация названий и вычисление количеств остаются небольшими функциями. Не вводим универсальный BaseService или BaseRepository без повторяющейся реальной задачи.

Предполагаемая структура (директории кода создаются при реализации):

```text
backend/
  pyproject.toml
  src/recipebook/
    main.py
    config.py
    api/             # routes, HTTP schemas, dependencies, errors
    domain/          # recipe, quantity, semantic validation
    services/        # recipe, conversation, drafts, auth
    repositories/    # persistence boundaries
    db/              # SQLAlchemy models, engine, transaction handling
    llm/             # protocol, LangChain adapter, prompts, validation
  migrations/
  tests/
frontend/
  package.json
  src/
    app/
    api/             # generated contract + HTTP client
    features/        # library, recipe, editor, chat
    shared/          # controls, quantity formatting, design tokens
schemas/
docs/
.env                 # server only, ignored
.env.example         # documented settings, no credentials
.python-version      # RecipeBook
```

Детали модулей описаны в backend-design.md, frontend-design.md, llm-design.md. Имена HTTP-полей и коды ошибок определяет api-contract.md; при расхождениях сначала исправляем этот контракт, затем документы модулей.

## Схема как общий договор

На этапе проектирования JSON Schema — проверяемый договор. При реализации создаём модели Pydantic и проверку эквивалентности ограничений с существующим примером. Затем фиксируем Pydantic как источник генерации JSON Schema и OpenAPI, а типы TypeScript генерируем из OpenAPI. Не поддерживаем три независимо редактируемые схемы.

RecipeContent, данные хранения, LLM draft и состояние просмотра имеют разные типы. Модель не получает право записи в БД. Её ответ проходит проверку и сохраняется как черновик. Подтверждение черновика — отдельная транзакция с проверкой ревизии. Пользовательские заметки принадлежат пользователю.

## Конфигурация и секреты

Settings загружается один раз из .env в корне проекта, с приоритетом переменных процесса. Путь определяется относительно проекта, а не случайного cwd. Значения токенов, ключей, разрешённый Telegram ID не находятся в исходниках. .env.example содержит только названия и безопасные значения по умолчанию.

Пустые LLM_API_KEY или LLM_MODEL выключают модель, но не ручные функции. Пустые настройки Telegram не включают обход авторизации: приватные API недоступны. Production отказывается запускаться без обязательной конфигурации и HTTPS PUBLIC_APP_URL. Сессионные токены генерируются криптографически сервером; в БД хранится только их SHA-256 хеш. Отдельный статический секрет для непрозрачных сессий не нужен.

Не выводим Settings целиком, заголовки Authorization, cookie, initData, тела чатов и .env в логи. Логи содержат request ID, код результата, время, модель и расход токенов без текста рецепта. VITE_* переменные считаются публичными; секретов в них нет. Реальные ключи пользователь вводит в локальный .env, а не в сообщения чата.

## Окружения и эксплуатация

Python-окружение pyenv RecipeBook уже существует: Python 3.11.11. Команды Python запускаются через PYENV_VERSION=RecipeBook pyenv exec. Node-пакеты устанавливаются только в frontend/node_modules, без глобальных установок. При реализации фиксируем версии и lock-файлы отдельно для Python и фронтенда.

Рабочие, тестовые и production базы разделены; тесты используют временную SQLite. Тесты LLM используют fake adapter и записанные обезличенные ответы. Настоящие API-вызовы — отдельный явно запускаемый набор, не часть обычного тестового прогона.

В проекте пока нет .git. На этом этапе агенты разделили владение файлами; это предотвращает пересечение правок, но не является изоляцией процессов. После создания Git-репозитория независимые ветви реализации можно вести в отдельных worktree. .gitignore подготовлен до появления каких-либо секретов.

Для размещения достаточно одного сервера с постоянным диском. Бэкап SQLite делается через SQLite backup API, а не копированием открытого файла с WAL; проверяется восстановление на отдельной базе. Миграции выполняются перед запуском новой версии с предварительным бэкапом. Конкретный хостинг ещё не выбран.

## Порядок реализации

1. Каркас FastAPI, Settings, Pydantic RecipeContent, SQLite и миграции. Проверить схему, диапазоны, ссылки ингредиентов и ревизии.
2. Telegram auth и ручной CRUD. Получить рабочую библиотеку без LLM, включая фильтры и заметки.
3. React Mini App: библиотека, редактор, карточка, порции и два режима шагов. Проверить на узком экране и в Telegram.
4. Чат и fake provider, сохранение черновиков, ошибки и повторные запросы. Проверить весь путь без платного API.
5. Подключить выбранную модель через отдельный адаптер. Проверить на небольшом наборе рецептов, замены продуктов и последовательных изменений.
6. HTTPS-размещение, резервные копии, smoke-проверка авторизации и доступ с телефона/компьютера.

Критерий готовности v1: рецепт можно создать и изменить вручную, получить из диалога, сохранить явным действием, найти по времени/продуктам и приготовить с пересчётом порций. Ошибка модели не повреждает сохранённые данные.

Перед живой интеграцией потребуются настройки бота, реальный доступ к провайдеру и выбор модели. Перед публикацией — адрес и способ размещения. Они не препятствуют проектированию и ручной версии; если возникнет неразрешимое противоречие, работа по зависимому сценарию останавливается для вопроса пользователю.
