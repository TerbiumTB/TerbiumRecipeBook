# Интеграция языковой модели

Статус: проект архитектуры v1, 24 октября 2026. Реализация, выбор конкретной модели и платные проверки ещё не выполнены.

## Границы ответственности

LLM помогает выбрать блюдо, составляет рецепт, отвечает на вопросы и предлагает полную новую редакцию рецепта. Поиск библиотеки, пересчёт порций, авторизация, запись в БД, проверка версий и пользовательские заметки остаются обычным Python-кодом. Для первой версии достаточно одного вызова модели на сообщение и ограниченного повторения при ошибке. Агентный цикл, LangGraph, RAG, векторная БД и доступ модели к инструментам не требуются.

Предлагаемые модули:

- `services/assistant_service.py`: собирает контекст, проверяет бюджет, вызывает адаптер, проверяет результат, сохраняет сообщения и предложение рецепта.
- `domain/assistant.py`: независимые от провайдера типы контекста, результата и ошибок.
- `llm/langchain_adapter.py`: настройка провайдера, структурированный вывод, преобразование ошибок и статистики.
- `llm/prompts/`: версионируемые инструкции и короткие примеры. Пользовательский текст не подставляется в системные инструкции.
- `llm/fake_adapter.py`: заранее заданные ответы для разработки и тестов без ключа и сети.

Классы нужны для адаптеров с конфигурацией и сервиса с зависимостями. Чистые преобразования, проверка ссылок и сборка контекста остаются функциями. Базовый интерфейс — `async reply(context: AssistantContext) -> AssistantResult`; домен не импортирует LangChain. Статистика и технический статус передаются отдельно от пользовательского содержимого.

LangChain допускает прямой вызов модели и структурированный вывод без создания агента. Используем этот путь внутри адаптера. Поддержку конкретного провайдера проверяем отдельно, зависимости фиксируем lock-файлом. [Документация LangChain](https://docs.langchain.com/oss/python/langchain/models#structured-output)

## Формат модельного результата

Внутренний объект `ModelReply`:

```json
{
  "message": "Предлагаю три варианта. Какой приготовим?",
  "ideas": [
    {"title": "Паста с томатами", "description": "Простой вариант с базиликом."}
  ],
  "recipe": null
}
```

`message` — непустой текст ответа; `ideas` — от нуля до пяти вариантов; `recipe` — `RecipeDraft` или `null`. Все три ключа обязательны. Идеи имеют короткое название и описание; свои ID им присваивает сервер. Уточняющий вопрос и обычное объяснение используют пустой массив идей и `recipe: null`. Готовый рецепт передаётся объектом, а не Markdown или JSON внутри строки. Отказ провайдера обрабатывается отдельно от `ModelReply`.

`RecipeDraft` совпадает по кулинарному содержимому с [канонической схемой](../schemas/recipe.schema.json), но не содержит `schemaVersion` и `userNotes`. Общие вложенные типы ингредиента, количества и шага переиспользуются в Pydantic; каноническая схема остаётся контрактом. При реализации генерация JSON Schema из Pydantic и тест соответствия экспортируемой схемы должны исключить расхождение определений.

Метаданные записи, ID чата и сообщений, даты, `revision`, `source`, `sourceConversationId`, версия схемы, ID нормализованных продуктов не генерируются моделью. `userNotes` не отправляем модели по умолчанию, не принимаем из её ответа и не заменяем при применении предложений.

Локальные ID ингредиентов и шагов нужны модели для ссылок. При изменении она сохраняет известные ID из контекста; для новых элементов выдаёт временные уникальные ID. Сервер проверяет ссылки, сохраняет известные ID, назначает новые локальные ID новым элементам и согласованно заменяет ссылки в шагах. Модель не получает права выбирать идентификаторы записей БД. В v1 при изменении семантики существующего элемента сохраняется его локальный ID; отдельной автоматической сверки ингредиентов по названию нет.

## Структурированный вывод и проверка

Для OpenAI выбираем режим Structured Outputs, если его поддерживает настроенная модель; адаптер получает Pydantic/JSON Schema, а не просьбу «ответь JSON». Провайдер поддерживает подмножество JSON Schema; JSON mode сам по себе не гарантирует соответствия схеме. Необходима отдельная обработка отказа и неполного ответа. [Official OpenAI documentation: Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)

Схема, отправляемая провайдеру, является производной от доменных типов. Адаптер может убрать неподдерживаемое ограничение, только сохранив его проверку на сервере. Общая схема рецепта не ослабляется ради провайдера. Не переключаемся незаметно с проверки схемы на свободный текст. Неподдерживаемая конфигурация даёт явную ошибку и исправляется до реального использования.

Последовательность обработки:

1. Проверить завершение генерации и отсутствие отказа до разбора JSON.
2. Проверить типы, обязательные поля, запрет лишних полей и размеры входа через Pydantic.
3. Проверить `activeMinutes <= totalMinutes`, положительные количества, `min <= max`, непустой текст, уникальность ID и существование `ingredientIds`.
4. Нормализовать новые локальные ID, добавить серверную `schemaVersion`, подготовить содержимое предложения без `userNotes`. При отдельном сохранении сервер собирает `RecipeContent`, добавляя актуальные заметки пользователя (для нового рецепта — пустую строку).
5. Сохранить предложение в сообщении чата. Сохранённый рецепт библиотеки не изменять.

Пределы сервиса для v1: до 60 ингредиентов, 40 шагов, 4000 символов инструкции шага и 500 символов описания идеи. Это защита ресурсов для модельного пути; изменение публичной схемы требует отдельной синхронизации контракта. Неиспользованные ингредиенты дают предупреждение. Проверка схемы не доказывает, что блюдо будет вкусным или что кулинарная рекомендация верна.

## Диалог и сохранение

На каждый ход передаём системные инструкции, сообщение пользователя, ограниченную историю, явно выбранный контекст рецепта и последний актуальный черновик. Из старых ответов передаём текст и идеи, а большие старые варианты рецептов исключаем: один полный актуальный рецепт достаточен. Выбранная идея передаётся по ID исходного сообщения и ID идеи, сервер сам восстанавливает её содержимое.

Изменение рецепта возвращает полный новый объект. Объяснение, например «зачем обжаривать чеснок?», не обязано создавать новую редакцию. Несколько одновременных генераций в одном чате запрещены, чтобы не перемешивать ветки диалога.

Граница HTTP: `POST /api/v1/conversations/{id}/messages` получает текст и ссылку на контекст; отвечает цельным JSON после проверки. В первой версии клиент не собирает рецепт из потоковых фрагментов. Сохранение черновика — отдельное действие `POST /api/v1/drafts/{id}/save` с `If-Match` при обновлении. Внешний ответ содержит `message`, `ideas`, `recipeDraft`; `recipeDraft.content` не включает пользовательские заметки. Точные DTO, идемпотентность и коды ошибок задаёт [общий API-контракт](api-contract.md); внутренний `ModelReply` напрямую в HTTP не публикуется.

Черновик несёт исходную пару `recipeId + revision` вне содержимого. Если пользователь изменил рецепт с другого устройства, применение старого предложения получает конфликт; автоматического слияния нет. При успешном применении сервер сохраняет актуальные пользовательские заметки. Ручное редактирование заметок выполняется обычным CRUD и также защищается версией.

## Ошибки и повторы

| Ситуация | Действие сервиса |
| --- | --- |
| Временная сеть, 429, 5xx | Не более одного повтора с задержкой и учётом `Retry-After`, общего срока и бюджета |
| Неверный ключ, нет доступа к модели, несовместимая схема | Без повтора; безопасная техническая ошибка, детали только в очищенном журнале |
| Отказ модели | Ответ без черновика, статус отказа; не пытаемся обходить отказ повторными запросами |
| Обрыв / лимит вывода | Не публикуем частичный рецепт; явная ошибка с возможностью повторить вручную |
| Семантически невалидный рецепт | Не более одного исправляющего запроса с краткими ошибками валидатора; при повторной ошибке черновика нет |
| Нехватка локального бюджета | Не вызываем провайдера; показываем, какой лимит исчерпан |

Один пользовательский ход допускает максимум **два обращения к провайдеру суммарно**, включая транспортный повтор и исправление. Встроенные повторы SDK/LangChain отключаем либо учитываем тем же счётчиком. Не запускаем каскад автоматических fallback-моделей. Общий deadline по умолчанию 60 секунд; ожидание, сетевой запрос и исправление входят в него.

Ключ идемпотентности защищает повторную отправку из интерфейса: тот же запрос возвращает сохранённый результат, а иной payload с тем же ключом — конфликт. Ход сначала записывается как pending без открытой транзакции на время сети. После перезапуска неопределённый ход становится interrupted; его не отправляем повторно автоматически. Это предотвращает заведомые дубли, но не обещает exactly-once или отсутствие оплаты после сетевого таймаута.

## История, бюджет и конфигурация

История хранится в нашей БД до удаления пользователем; удаление чата не удаляет уже сохранённые рецепты. Удалённые сообщения не попадают в последующие запросы. Очистка резервных копий регулируется отдельным сроком хранения бэкапов. Провайдер получает только контекст текущего запроса; внутренние provider conversation ID не являются основой хранения приложения. Политика хранения данных самим провайдером проверяется при выборе подключения, без обещания полного отсутствия его журналов.

В контекст отправляем не более 12 последних завершённых пар сообщений плюс актуальный рецепт. Действуют также ограничение входных токенов и резерв выходных токенов. При переполнении сначала отбрасываем самые старые полные пары; текущий запрос, системные инструкции и выбранный рецепт не обрезаем. Если они одни не помещаются, возвращаем `context_too_large`. Интерфейс показывает, что старые сообщения исключены. Автоматическое платное суммирование не нужно в v1.

Секреты и конфигурация находятся в серверном `.env`, исключённом из Git, образов и фронтенд-сборки. В `.env.example` — пустые секреты и документированные значения. Токены не вводятся в чат разработки и не логируются. Параметры основного `.env.example` и предлагаемые дополнительные ограничения:

| Переменная | Назначение |
| --- | --- |
| `LLM_PROVIDER` | `openai` в шаблоне; `fake` для тестов и локальной разработки без сети |
| `LLM_MODEL` | Обязательный идентификатор для реального провайдера; без зашитого имени модели |
| `LLM_API_KEY` | Секрет выбранного провайдера, адаптер передаёт его явно |
| `LLM_BASE_URL` | Необязательный адрес только из серверной конфигурации, не из HTTP запроса |
| `LLM_TIMEOUT_SECONDS` | Общий deadline хода, предложение: `60` |
| `LLM_MAX_CONVERSATION_TOKENS` | Максимум входного контекста, включая системные инструкции и рецепт: `16000` |
| `LLM_MAX_OUTPUT_TOKENS` | Максимум ответа, предложение: `6000` |
| `LLM_DAILY_REQUEST_LIMIT` | Лимит обращений с учётом повторов, предложение: `50` |
| `LLM_DAILY_TOKEN_LIMIT` | Суммарный токеновый бюджет, предложение: `200000` |

Дневные лимиты — предлагаемые дополнительные параметры для этапа реализации; основной `.env.example` может пока их не включать. Числа — исходные ограничения продукта, а не характеристики выбранной модели. Адаптер проверяет, что сумма лимитов укладывается в её контекст и что токены посчитаны подходящим способом. До запроса атомарно резервируем верхнюю оценку расхода; после ответа списываем фактический usage. При неизвестном расходе после таймаута сохраняем резерв как потраченный до сверки. Если провайдер не даёт подходящей оценки, применяем консервативную границу размера либо не допускаем его в режим жёсткого токенового бюджета. Лимит в токенах не равен фиксированной денежной стоимости.

Журнал содержит request ID, провайдера, модель, версию промпта, длительность, тип ошибки и usage; без текста рецептов, сообщений, `initData`, ключей и заголовков авторизации. Сторонний tracing выключен по умолчанию. Выбор модели и денежного бюджета остаётся настройкой до первых реальных вызовов; неподтверждённые названия и цены не фиксируем.

## Проверка перед подключением модели

Сначала контрактные тесты на fake-адаптере: обычный ответ, идеи, полный рецепт, изменение с сохранением заметок, неверные ссылки, конфликт версии, отказ, обрыв, timeout, повторный request ID и исчерпание бюджета. Отдельно проверяем, что вывод модели не может обновить БД или поменять пользовательские заметки.

Для реального провайдера — небольшой заранее известный набор русских запросов: рецепт с нуля, идеи из продуктов, выбор идеи, две последовательные замены, ингредиент «по вкусу», диапазон количества и обычный вопрос без новой версии. Измеряем долю валидных рецептов, соблюдение пожеланий, задержку и расход токенов. Платные прогоны выполняются отдельно после настройки пользователем ключа и модели.

Смена провайдера требует пройти тот же набор проверок и проверить схему/ошибки/usage; совместимый URL API сам по себе не доказывает совместимость поведения. Внешний HTTP-контракт и формат сохранённых рецептов при этом не меняются.
